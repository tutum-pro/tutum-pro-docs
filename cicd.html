deployed_code tutum-cicd

info Overview

tutum-cicd is an Ansible Collection (tutum_pro.cicd) for automated deployment of the Tutum Platform. It provides idempotent roles for deploying all platform components on Docker hosts, with support for both embedded and external PostgreSQL databases.

check_circle Key Features
  • Full stack deployment automation
  • Docker platform support (Kubernetes coming soon)
  • Embedded or external PostgreSQL
  • Automatic database migrations
  • Idempotent operations
  • Ansible Galaxy distribution
build Technical Details
  • Collection: tutum_pro.cicd
  • Ansible: 2.14+
  • Platforms: Ubuntu, Debian, RHEL/CentOS
  • License: MIT

collections:

ansible-galaxy collection install tutum_pro-cicd-1.2.5.tar.gz -p ./collections

rocket_launch Quick Start

Using docker_tutum_init Role (Recommended)

The docker_tutum_init role generates installation playbook and inventory files:

# Generate installation files for localhost
ansible localhost -m include_role -a name=tutum_pro.cicd.docker.tutum_init

# Generate for remote host with SSH key authentication
ansible localhost -m include_role -a name=tutum_pro.cicd.docker.tutum_init \
  -e docker_tutum_init_target_host=192.168.1.100 \
  -e docker_tutum_init_target_hostname=docker-server-1 \
  -e docker_tutum_init_ansible_connection=ssh \
  -e docker_tutum_init_ansible_user=ansible \
  -e docker_tutum_init_ansible_ssh_key=~/.ssh/id_rsa

# Generate for remote host with SSH password authentication
ansible localhost -m include_role -a name=tutum_pro.cicd.docker.tutum_init \
  -e docker_tutum_init_target_host=192.168.1.100 \
  -e docker_tutum_init_target_hostname=docker-server-1 \
  -e docker_tutum_init_ansible_connection=ssh \
  -e docker_tutum_init_ansible_user=ansible \
  -e docker_tutum_init_ansible_ssh_pass=YourSSHPassword \
  -e docker_tutum_init_ansible_become_password=YourSudoPassword

# Run the generated playbook
ansible-playbook -i inventory/docker.ini tutum-install.yml

# Or use --ask-pass for interactive SSH password prompt
ansible-playbook -i inventory/docker.ini tutum-install.yml --ask-pass

Using Collection Playbooks

# Install full stack
ansible-playbook -i inventory/hosts.yml tutum_pro.cicd.site

# Install individual components
ansible-playbook -i inventory/hosts.yml tutum_pro.cicd.engine
ansible-playbook -i inventory/hosts.yml tutum_pro.cicd.plugin
ansible-playbook -i inventory/hosts.yml tutum_pro.cicd.cli

# Uninstall all (keeps data)
ansible-playbook -i inventory/hosts.yml tutum_pro.cicd.uninstall

# Uninstall with COMPLETE DATA REMOVAL (destructive!)
ansible-playbook -i inventory/hosts.yml tutum_pro.cicd.uninstall \
  -e docker_tutum_engine_remove_data=true \
  -e docker_tutum_postgres_remove_data=true \
  -e docker_tutum_plugin_remove_volumes=true
warning Complete Uninstallation

To completely remove Tutum Platform including all data, volumes, and certificates:

ansible-playbook -i inventory/docker.ini tutum_pro.cicd.uninstall \
  -e docker_tutum_engine_remove_data=true \
  -e docker_tutum_postgres_remove_data=true \
  -e docker_tutum_plugin_remove_volumes=true
VariableEffect
docker_tutum_engine_remove_data=trueRemoves tutum-engine container and data directory
docker_tutum_postgres_remove_data=trueRemoves PostgreSQL container and /var/lib/tutum/postgres data
docker_tutum_plugin_remove_volumes=trueRemoves plugin service and /var/lib/tutum/volumes

Custom Playbook with Embedded PostgreSQL

# site.yml
- name: Deploy Tutum Platform
  hosts: docker_servers
  become: true

  vars:
    docker_tutum_engine_version: "3.4.0"
    docker_tutum_master_key: "YourSecure32CharacterKeyHere!!!"
    docker_tutum_jwt_secret: "YourSecure32CharacterJwtSecret!"

  roles:
    - role: tutum_pro.cicd.docker.tutum_postgres
    - role: tutum_pro.cicd.docker.tutum_engine
    - role: tutum_pro.cicd.docker.tutum_plugin
    - role: tutum_pro.cicd.docker.tutum_cli

Custom Playbook with External PostgreSQL

# site.yml
- name: Deploy Tutum Platform (External DB)
  hosts: docker_servers
  become: true

  vars:
    docker_tutum_engine_version: "3.4.0"
    docker_tutum_external_db_url: "postgres://tutum:password@db.example.com:5432/tutum?sslmode=require"
    docker_tutum_master_key: "YourSecure32CharacterKeyHere!!!"
    docker_tutum_jwt_secret: "YourSecure32CharacterJwtSecret!"

  roles:
    # Note: tutum_postgres role is skipped when external DB is configured
    - role: tutum_pro.cicd.docker.tutum_engine
    - role: tutum_pro.cicd.docker.tutum_plugin
    - role: tutum_pro.cicd.docker.tutum_cli

The docker_tutum_rest_port and docker_tutum_grpc_port variables control host ports only. The container always listens on internal ports 8080 (REST) and 9090 (gRPC). This allows changing host ports without conflicts (e.g., -p 18080:8080).

storage Database Modes

Embedded PostgreSQL (Default)

PostgreSQL runs as a Docker container managed by the collection.

  • Automatic container deployment
  • Data persistence in /var/lib/tutum/postgres
  • Health checks configured
  • Migrations applied automatically

Use when: Development, testing, single-node deployments

External PostgreSQL

Connect to existing PostgreSQL instance.

  • Set docker_tutum_external_db_url
  • tutum_postgres role is skipped
  • Migrations still applied by tutum_engine
  • Requires postgresql-client on target host

Use when: Production, HA setups, managed databases (RDS, Cloud SQL)

security Production Deployment

Generate Secure Keys

# Generate 32-character keys
openssl rand -base64 32 | head -c 32

Using Ansible Vault

# Create encrypted vars file
ansible-vault create inventory/group_vars/vault.yml
# vault.yml contents
docker_tutum_master_key: "your-32-char-key-here-exactly!!"
docker_tutum_jwt_secret: "another-32-char-secret-here!!!!"
docker_tutum_db_password: "secure-database-password"
# Run with vault
ansible-playbook site.yml --ask-vault-pass
warning Security Notice
  • Always use Ansible Vault for sensitive variables in production
  • Master key and JWT secret must be exactly 32 characters
  • Back up your keys - losing them means losing access to encrypted certificates
  • Use TLS for external PostgreSQL connections (sslmode=require)

upgrade Database Migrations

tutum-engine automatically runs database migrations on startup. Migrations are idempotent and safe to run multiple times. Below is a list of all migrations with their descriptions.

info Migration Behavior
  • Migrations run automatically when tutum-engine starts
  • Each migration runs exactly once (tracked in schema_migrations table)
  • Migrations are transactional - if one fails, it is rolled back
  • New migrations are added with sequential numbering (000, 001, 002...)

Migration History

IDNameDescription
000 add_pid_columns Adds internal pid (primary id) columns to all tables for efficient foreign key relationships
001 add_versioning Implements certificate versioning system - splits certificates into certificate_metadata (immutable) and certificate_versions (versioned content)
002 update_audit_logs_constraints Updates audit_logs table constraints for better data integrity
003 unique_name_per_group_namespace Adds unique constraint: certificate name must be unique within (group_id, namespace)
004 add_workload_to_audit_log Adds workload tracking columns to audit_logs (workload_type, workload_name, workload_namespace)
005 add_version_requested_to_audit_log Adds version_requested column to track which certificate version was requested
006 populate_group_names Backfills group names from certificate_groups to certificate_metadata for denormalization
007 add_pod_restart_config_to_namespaces Adds pod restart configuration columns to namespaces table
008 add_distribution_channels Creates distribution_channels table for certificate distribution with authentication tokens
009 move_channel_to_certificates Moves channel association from versions to certificate_metadata for better data model
010 add_type_column_and_update_constraints Adds type column (X509, secret) to support both certificates and generic secrets
011 add_uuid_to_audit_logs Adds UUID primary key to audit_logs for better distributed system support
012 add_is_effective_column NEW in v3.4.0: Adds is_effective and effective_since columns for automatic certificate version activation based on validity windows.
See Certificate Validity Management in engine docs.

Migration 012: Effective Version Management

This migration enables automatic certificate activation/deactivation based on validity windows (not_before and not_after dates).

Schema Changes
-- New columns
ALTER TABLE certificate_versions
ADD COLUMN is_effective BOOLEAN DEFAULT FALSE;

ALTER TABLE certificate_versions
ADD COLUMN effective_since TIMESTAMP;

-- Unique constraint (only one effective per cert)
CREATE UNIQUE INDEX
  idx_certificate_versions_one_effective
ON certificate_versions (certificate_metadata_pid)
WHERE is_effective = TRUE;
New Views
  • certificates_latest - prefers is_effective=true, fallback to latest version
  • certificates_effective - only certificates with effective version (for CSI driver)

The effective version is selected by the Go algorithm in tutum-engine based on: validity window + longest time until expiry.

warning Upgrade Notes for v3.4.0
  • Automatic activation: Existing certificates will have their effective version set on first scheduler run (within 5 minutes of startup)
  • gRPC API change: ListCertificates now defaults to returning only effective certificates. Use include_all=true for all certificates.
  • New audit actions: ACTIVATE, DEACTIVATE, RESTART appear in audit logs when certificate validity changes
  • Scheduler configuration: New env vars TUTUM_VALIDITY_CHECKER_CRON and TUTUM_WORKLOAD_RESTARTER_CRON

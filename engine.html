add_circle 1. Certificate Creation (Adding Certificates)

Overview

Certificate creation is the process of storing X.509 certificates in the Tutum Platform with full encryption and metadata extraction. The system supports both certificate creation and updates with automatic versioning.

Creation Flow

sequenceDiagram participant Client as REST Client participant API as REST API participant Service as Certificate Service participant Enc as Encryption Service participant KM as Key Manager participant DB as PostgreSQL participant K8s as K8s Pod Restarter participant Audit as Audit Service Client->>API: POST /api/v1/certificates API->>API: Validate request payload API->>Service: Create(certificate) Service->>Service: Parse X.509 certificate Service->>Service: Extract metadata (subject, issuer, SANs, expiry) Service->>Enc: Encrypt private key Enc->>KM: GenerateDEK() KM-->>Enc: DEK (256-bit) Enc->>Enc: Encrypt private key with DEK (AES-256-GCM) Enc->>KM: EncryptDEK(dek) KM-->>Enc: Encrypted DEK Enc-->>Service: Encrypted payload Service->>DB: INSERT certificate (version=1) DB-->>Service: Success Service->>Audit: Log CREATE action Service->>K8s: Trigger pod restart (if applicable) Service-->>API: Certificate created API-->>Client: 201 Created + certificate response
description Diagram Explanation

The certificate creation flow begins when a REST client sends a POST request to the /api/v1/certificates endpoint. The REST API layer first validates the incoming request payload to ensure all required fields are present and properly formatted.

Once validated, the request is forwarded to the Certificate Service, which performs two critical operations: parsing the X.509 certificate to validate its structure, and extracting metadata such as subject, issuer, Subject Alternative Names (SANs), and expiration dates.

The private key then undergoes envelope encryption through the Encryption Service. First, the Key Manager generates a unique Data Encryption Key (DEK) - a 256-bit random key. The private key is encrypted using this DEK with the AES-256-GCM algorithm. Then, the DEK itself is encrypted using the Master Key, creating a secure "envelope" around the sensitive data.

With the encrypted payload ready, the Certificate Service stores the certificate in PostgreSQL with version=1 for new certificates. The Audit Service logs the CREATE action for compliance tracking. If applicable (when the certificate replaces an existing one used by workloads), the K8s Pod Restarter is triggered to perform rolling restarts of affected deployments.

Finally, the API returns a 201 Created response with the certificate details (excluding the decrypted private key in the response for security).

Automatic Metadata Extraction

When a certificate is created, the system automatically extracts and stores comprehensive metadata from the X.509 certificate structure. This metadata serves multiple purposes: enabling search and filtering capabilities, providing visibility into certificate properties, and calculating status based on validity dates. The extraction is performed using Go's crypto/x509 package, which parses the DER-encoded certificate data and exposes all standard X.509 fields.

Versioning

Each certificate update creates a new version:

  • Create: Creates version 1
  • Update: Increments version (1 → 2 → 3...)
  • Retrieve: By default returns latest version; specific version can be requested
  • History: All versions are preserved and can be listed via /api/v1/certificates/{name}/versions

Auto-Creation of Groups/Namespaces

When CREATE_NOT_EXISTING_OBJ=true:

  • If group_name is provided but group doesn't exist → automatically created
  • If namespace doesn't exist → automatically created with default channel
  • Useful for CI/CD pipelines that need to create certificates dynamically
warning
Security Note: Private keys are never stored in plaintext. They are encrypted using envelope encryption (AES-256-GCM) with a unique DEK per certificate, which is itself encrypted with the Master Key.

security 1.4 Secret Architecture - Design Assumptions

gpp_maybe
Security by Design: This section describes the fundamental security assumptions behind the secret management architecture. Understanding these assumptions is critical for proper deployment and operation of the Tutum Platform.

Dual Role of Secrets

In the Tutum Platform, secrets serve two distinct purposes, each with different security requirements:

password Role 1: Certificate Passphrases

Purpose: Passwords protecting X.509 private keys

Relationship: Linked to X.509 certificates via matching name/namespace/group

Lifecycle: Synchronized with certificate validity period

Example use cases:

  • PKCS#12/PFX export passwords
  • Encrypted private key passphrases
  • HSM PIN codes
database Role 2: Standalone Secrets

Purpose: Generic confidential data unrelated to certificates

Relationship: Independent objects (no linked X.509)

Lifecycle: User-defined or default +100 years

Example use cases:

  • Database connection passwords
  • Message queue credentials (RabbitMQ, Kafka)
  • External API keys and tokens
  • Kubernetes Secrets compatible distribution

Security Architecture: Channel Separation

key

MFA Analogy: Defense in Depth

The separate distribution of certificates and secrets follows the same principle as Multi-Factor Authentication:

login Traditional MFA
  • Factor 1: Password (something you know)
  • Factor 2: Phone/Token (something you have)
  • Result: Attacker needs both to authenticate
verified_user Tutum Secret Distribution
  • Channel 1: X.509 Certificate (via CSI Driver / gRPC)
  • Channel 2: Passphrase Secret (via REST API / different token)
  • Result: Attacker needs both to decrypt private key
Practical Example: A Kubernetes workload receives the X.509 certificate via the CSI driver (gRPC channel with workload authentication), while the passphrase is injected via a separate Kubernetes Secret synchronized from Tutum (REST API channel with different token). An attacker who compromises the CSI communication cannot decrypt the private key without also compromising the secret distribution path.

Linking Secrets to Certificates

When a secret should function as a certificate passphrase, it is linked by naming convention:

Certificate Identity:
  name:      "my-app-tls"
  namespace: "production"
  group_id:  "web-servers"

Linked Secret Identity (must match all three):
  name:      "my-app-tls"        ← same name
  namespace: "production"        ← same namespace
  group_id:  "web-servers"       ← same group

Effect: When both exist, the secret's validity period is automatically constrained to the X.509 certificate's bounds (see Validity Period Rules).

lightbulb
Design Rationale: Using naming convention instead of explicit foreign keys provides flexibility - secrets can exist before their certificates (useful in CI/CD pipelines), and the relationship is automatically discovered. This loose coupling also enables the two-channel distribution model.

Summary: Design Decisions

  1. Secrets as separate objects - Not embedded in certificates, enabling independent access control, audit, and distribution channels.
  2. Channel separation (MFA model) - Certificates and secrets distributed via different APIs/tokens, requiring compromise of multiple paths for full access.
  3. Independent encryption keys - Each object (cert/secret) has its own DEK, limiting blast radius of key compromise.
  4. Naming-based linking - Flexible association via name/namespace/group matching, enabling loose coupling and CI/CD-friendly workflows.
  5. Validity period synchronization - Passphrase secrets automatically inherit certificate validity bounds, preventing orphaned credentials.
  6. K8s Secrets compatibility - Standalone secrets can be synchronized to native Kubernetes Secrets for standard workload consumption.

key 1.5 Secret Management - Validity Period Rules

Overview

Tutum Platform supports not only X.509 certificates but also generic secrets (passwords, API keys, tokens, etc.). Secrets are stored encrypted using the same envelope encryption mechanism as certificates, but with specialized validity period rules that can be linked to associated X.509 certificates.

info
Key Concept: Secrets can share the same name, namespace, and group as an X.509 certificate. When this happens, the secret's validity period is automatically linked to the certificate's validity bounds.

Secret Types vs X.509 Certificates

Aspect X.509 Certificate Secret
Type Parameter type=X509 (default) type=secret
Payload x509.certificate, x509.private_key, x509.ca_chain secret.data
Validity Period Extracted from X.509 certificate (notBefore, notAfter) Defined in payload or derived from linked X.509
Metadata Automatically extracted (subject, issuer, SANs, fingerprint, etc.) Only custom_metadata (user-defined)
Encryption Private key encrypted with envelope encryption Entire secret data encrypted with envelope encryption

Secret Validity Period Rules

The validity period of a secret is determined by a set of business rules that consider whether an X.509 certificate with the same identity (name, namespace, group) exists.

priority_high
Important: These rules ensure that secrets don't outlive their associated X.509 certificates, maintaining security consistency across the platform.

Decision Matrix

Scenario X.509 Certificate Exists? Validity Period in Request? Result
Rule 1 No No Default: +100 years (effectively never expires)
Rule 2 No Yes Use requested period (validate not_before < not_after)
Rule 3 Yes No Copy validity from effective X.509 version (or +100 years if no effective)
Rule 4 Yes Yes Constrain to X.509 bounds (intersection with matching versions)

Rule 1: No X.509, No Period Defined

Condition: Secret created without a matching X.509 certificate, and no not_before/not_after specified.

Behavior: Secret is assigned a validity period of now to now+100 years, effectively making it permanent.

Use Case: Standalone secrets like API keys that don't expire.

Rule 2: No X.509, Period Defined

Condition: Secret created without a matching X.509 certificate, but with not_before and/or not_after specified.

Behavior: Uses the requested validity period after validation.

Validation: not_before must be strictly before not_after. Otherwise, returns error ErrSecretInvalidPeriod.

Use Case: Time-limited secrets like temporary access tokens.

Rule 3: X.509 Exists, No Period Defined

Condition: X.509 certificate with matching (name, namespace, group) exists, and no validity period specified in secret request.

Behavior:

  • If X.509 has an effective version (version with is_effective=true): Copy not_before and not_after from that version.
  • If X.509 has no effective version: Fall back to default +100 years.

Use Case: Private key passwords or decryption keys that should share the same lifecycle as the certificate.

Rule 4: X.509 Exists, Period Defined

Condition: X.509 certificate exists AND validity period specified in secret request.

Behavior:

  1. Find all X.509 versions whose validity periods overlap with the requested secret period.
  2. If no overlapping versions found: Return error ErrSecretNoMatchingX509.
  3. If overlapping versions found: Merge their periods (earliest not_before to latest not_after).
  4. Constrain the secret's period to the intersection with merged X.509 bounds.

Use Case: Secrets that must be valid only during specific certificate versions' validity windows.

Runtime Validity Enforcement

gpp_maybe
Security Feature: The gRPC API enforces secret validity at runtime. Secrets outside their validity window (not_before to not_after) are not returned to clients.

When a client (e.g., CSI driver) requests a secret via gRPC:

  1. The system checks if the secret has is_effective = true
  2. For secrets, additionally checks if now() is between not_before and not_after
  3. If the secret is outside its validity window, an error is returned instead of the secret data

The REST API retrieval process begins with a GET request specifying the certificate name and filtering parameters (group and namespace). The REST API forwards this request to the Certificate Service, which queries PostgreSQL for the encrypted certificate data.

A critical security check follows: the Namespace Service is consulted to determine the namespace's confidentiality level. This is where the two paths diverge:

verified 4. Certificate Validity and Effective Version Management

Overview

tutum-engine implements an intelligent certificate validity management system that automatically activates and deactivates certificate versions based on their validity windows. This ensures that workloads always receive the correct, currently valid certificate version without manual intervention.

lightbulb
Key Concept: Each certificate can have multiple versions. Only one version can be marked as is_effective=true at any given time. This is the version that will be distributed to workloads via gRPC API.

Effective Version Selection Algorithm

The algorithm runs periodically (default: every 5 minutes) and evaluates all certificate versions to determine which one should be effective. The selection criteria are:

filter_alt Step 1: Filter Valid Candidates

Only versions meeting ALL criteria are considered:

  • not_before <= NOW() - Version is already valid (validity period has started)
  • not_after >= NOW() - Version has not expired yet
  • status NOT IN ('REVOKED', 'INVALID') - Version is not revoked or marked invalid
sort Step 2: Sort by Priority

Candidates are sorted by:

  1. Longest time until expiry (not_after - NOW()) DESC - Prefer versions that will remain valid longest
  2. Highest version number version DESC - Tiebreaker: prefer newer versions
check_circle Step 3: Set Effective

The first candidate after sorting becomes the effective version (is_effective = TRUE). All other versions have is_effective = FALSE.

Change Types

When the algorithm runs, it detects one of four possible outcomes for each certificate:

Change TypeConditionDescription
NO_CHANGE Same version remains effective No action needed. The currently effective version is still the best choice.
ACTIVATED No version was effective → new version becomes effective A certificate that had no valid versions now has one. Workloads can start using this certificate.
DEACTIVATED Version was effective → no version is now effective All versions are now expired, revoked, or invalid. Workloads will be notified that the certificate is unavailable.
VERSION_CHANGE Different version becomes effective Algorithm selected a different version (e.g., newer version entered validity window, or current version is expiring soon).

Scheduler Architecture (Two-Phase Design)

The system uses two separate schedulers following the Shannon-Nyquist theorem for signal processing to ensure no changes are missed:

Why two schedulers? Separating validity checking from workload restarting provides several benefits:

  • Decoupling: Database updates and Kubernetes API calls are independent operations with different failure modes
  • Reliability: If workload restart fails, the database state is already correct
  • Performance: Scheduler A can process thousands of certificates quickly; Scheduler B handles slower K8s operations

Shannon-Nyquist Theorem: To accurately detect all changes from Scheduler A (5 min interval), Scheduler B must sample at least twice as frequently (2.5 min = 5 min / 2). This ensures no certificate changes are missed.

Communication: Changes are passed via an in-memory store (EffectiveVersionChangeStore) using thread-safe operations. Scheduler B atomically pops all pending changes on each run.

restart_alt 6. Kubernetes Deployment Restart with Rate Limiting

Overview

When a certificate is created or updated, tutum-engine can automatically trigger a rolling restart of Kubernetes workloads (Deployments, StatefulSets, DaemonSets) that are using that certificate. This ensures workloads always have the latest certificate without manual intervention.

warning
Flapping Protection: To prevent "certificate flapping" (rapid updates causing continuous pod restarts), the system implements multiple protection mechanisms described below.

Restart Flow

sequenceDiagram participant API as REST API participant Service as Certificate Service participant Audit as Audit Service participant Restarter as Pod Restarter participant Dedup as Deduplication participant RL as Rate Limiter participant CB as Circuit Breaker participant Backoff as Backoff Calculator participant K8s as Kubernetes API API->>Service: Create/Update certificate Service->>Service: Save certificate Service->>Audit: Query workloads mounting this certificate Audit-->>Service: List of workloads (from MOUNT actions) loop For each workload Service->>Restarter: RestartWorkload(type, name, namespace) Restarter->>Dedup: Check duplicate (30s window) alt Duplicate request Dedup-->>Restarter: BLOCKED (duplicate) else Not duplicate Restarter->>RL: Check rate limit (3/15min) alt Rate limit exceeded RL-->>Restarter: BLOCKED (rate limited) else Within rate limit Restarter->>CB: Check circuit breaker alt Circuit OPEN CB-->>Restarter: BLOCKED (circuit open) else Circuit CLOSED/HALF_OPEN Restarter->>Backoff: Calculate delay Backoff-->>Restarter: Delay (0s/30s/2m/5m/15m) Restarter->>Restarter: Wait delay Restarter->>K8s: PATCH Deployment (update annotation) alt Success K8s-->>Restarter: OK Restarter->>CB: Record success else Failure K8s-->>Restarter: Error Restarter->>CB: Record failure end end end end end
description Restart Flow Explanation

When a certificate is created or updated via the REST API, the Certificate Service triggers a cascade of events to ensure all consuming workloads receive the new certificate. The process begins by querying the Audit Service for all MOUNT actions related to this certificate, which reveals which Kubernetes workloads are currently using it.

For each discovered workload, the Pod Restarter initiates a restart request. However, before any restart actually occurs, the request passes through a multi-layer protection pipeline designed to prevent "certificate flapping" - a condition where rapid certificate updates cause continuous pod restarts, leading to service instability.

Layer 1 - Deduplication: The first check prevents duplicate restart requests within a 30-second window. If the same workload already received a restart request recently, the new request is silently ignored. This handles the case of multiple rapid certificate updates.

Layer 2 - Rate Limiting: Even if the request passes deduplication, it must comply with the rate limit of 3 restarts per workload per 15-minute window. Excess requests are queued or rejected, preventing a certificate update storm from overwhelming the cluster.

Layer 3 - Circuit Breaker: The circuit breaker monitors the success rate of restart operations. If the circuit is OPEN (due to consecutive failures), all restart requests are blocked until the recovery timeout expires. This prevents the system from repeatedly trying to restart workloads that are failing for external reasons.

Layer 4 - Exponential Backoff: Finally, if all checks pass, the backoff calculator determines the delay before executing the restart. The first restart happens immediately, but subsequent restarts face increasing delays (30s, 2m, 5m, 15m) to give the cluster time to stabilize.

The actual restart is performed by patching the workload's pod template annotation (tutum.io/restartedAt), which triggers Kubernetes' native rolling restart mechanism.

stateDiagram-v2 [*] --> CLOSED CLOSED --> OPEN: 5 consecutive failures OPEN --> HALF_OPEN: After 15 minutes HALF_OPEN --> CLOSED: 1 successful restart HALF_OPEN --> OPEN: 1 failed restart note right of CLOSED: Normal operation\nAll restarts allowed note right of OPEN: Protection mode\nAll restarts blocked note right of HALF_OPEN: Testing recovery\n1 restart allowed
description Circuit Breaker States Explanation

The circuit breaker pattern is a resilience mechanism borrowed from electrical engineering. Just as an electrical circuit breaker trips to prevent damage from overload, this software circuit breaker "trips" to prevent cascading failures in the Kubernetes cluster.

CLOSED (Normal Operation): This is the healthy state. All restart requests pass through the circuit breaker to the Kubernetes API. Each successful restart keeps the circuit closed, and the failure counter remains at zero.

OPEN (Protection Mode): When 5 consecutive restart attempts fail (e.g., due to Kubernetes API errors, network issues, or RBAC problems), the circuit breaker trips to the OPEN state. In this state, all restart requests are immediately rejected without attempting to contact the Kubernetes API. This prevents resource waste and gives the cluster time to recover from whatever issue caused the failures.

HALF_OPEN (Recovery Testing): After 15 minutes in the OPEN state, the circuit breaker transitions to HALF_OPEN. This is a probe state that allows exactly one restart request to pass through. If this request succeeds, the circuit closes and normal operation resumes. If it fails, the circuit opens again for another 15-minute recovery period.

This state machine ensures that the system can automatically recover from transient failures while still protecting against persistent problems that could destabilize the cluster.

Envelope Encryption Architecture

description Envelope Encryption Explanation

Envelope encryption is a two-layer encryption strategy that provides both security and key management flexibility. The name comes from the concept of placing data in a "secure envelope" - the inner layer protects the data, while the outer layer protects the key.

Why not encrypt directly with the Master Key? If we encrypted every private key directly with the Master Key, rotating that key would require decrypting and re-encrypting every certificate in the database - a risky and time-consuming operation. Envelope encryption solves this by using a unique Data Encryption Key (DEK) for each certificate.

The Encryption Process:

  1. DEK Generation: A cryptographically secure 256-bit random key is generated for each certificate. This key is never reused and exists only in memory during the encryption operation.
  2. Data Encryption: The private key is encrypted using AES-256-GCM with the DEK. GCM mode provides both confidentiality (encryption) and integrity (authentication tag), ensuring the data cannot be modified without detection.
  3. DEK Encryption: The DEK itself is encrypted with the Master Key, creating the "envelope". Only the encrypted DEK is stored alongside the encrypted data.
  4. Storage: The final payload contains the encrypted private key, the encrypted DEK, the GCM nonce, and the authentication tag - all Base64 encoded for safe storage in PostgreSQL.

Key Rotation Benefit: When the Master Key needs to be rotated, only the DEKs need to be re-encrypted (decrypt with old Master Key, re-encrypt with new Master Key). The actual certificate data remains untouched, making rotation fast and safe.
